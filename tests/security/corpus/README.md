# Malicious-PDF Corpus

Synthetic PDF payloads from
[`jonaslejon/malicious-pdf`](https://github.com/jonaslejon/malicious-pdf),
pinned to commit `c33050c637c75dfd9bea8afcabad0f41a928c070`.

## What's here

- `manifest.json` — committed. One record per payload mapping each
  PDF to PDFE attack surface, expected behavior, sha256, and the
  upstream payload ID.
- `malicious_pdf/SOURCE.txt` — committed. Provenance, AV interference
  notes, callback host.
- `malicious_pdf/*.pdf` `*.svg` `*.xml` — **gitignored**. Generated by
  `scripts/security/gen_malicious_corpus.ps1`.

## Why these aren't checked in

The payloads are designed to phone home to a callback host (we use
`127.0.0.1:9999`). Even though the callback is loopback-only, shipping
70 payload files in repo history would:

1. Trigger every contributor's antivirus on clone
2. Make the repo flagged by GitHub's secret/malware scanners
3. Encourage someone to accidentally open one outside the sandboxed
   runner

So the convention is: commit the generator + manifest, regenerate
on demand, never persist payloads to history.

## How to regenerate

```powershell
.\scripts\security\gen_malicious_corpus.ps1
```

This:

1. Clones (or refreshes) `jonaslejon/malicious-pdf` at the pinned SHA
   in `$env:TEMP\pdfe_malicious_pdf_clone`.
2. Runs `python malicious-pdf.py 127.0.0.1 --output-dir <corpus>`.
3. Rebuilds `manifest.json` via `scripts/security/build_manifest.py`.

## Antivirus interference

**Read this before running phase 3.**

Windows Defender (and most enterprise AV products) flag many of
these payloads as malware because they contain real exfiltration
patterns and the EICAR test signature.

Without an AV exclusion, expect anywhere from 1 to 60+ payloads to
silently disappear during generation. The manifest builder reports
exactly which upstream IDs are present so coverage gaps are visible:

```
$ python scripts/security/build_manifest.py --corpus ... --out ...
wrote manifest.json (69 payloads, 0 unmapped)    # or
wrote manifest.json (45 payloads, 0 unmapped)    # AV got 25 of them
```

To make the corpus complete:

1. Open Windows Security → Virus & threat protection → Manage
   settings → Add or remove exclusions.
2. Add a folder exclusion for the absolute path of
   `tests/security/corpus/malicious_pdf/` in this checkout.
3. (Optionally) Also exclude `$env:TEMP\pdfe_malicious_pdf_clone\`
   so the upstream generator's `output/` working dir is also clean.
4. Re-run `gen_malicious_corpus.ps1`.

The phase-3 runner (`tests/security/runner/run_corpus.py`, lands in
phase 3) walks `manifest.json` and runs each listed payload — it
does not ad-hoc discover files. So if AV deleted `test11.pdf`,
phase 3 simply skips that ID and notes it in the report. **A
corpus shorter than the canonical 70 is reported as a coverage
gap, not silently treated as success.**

## Per-category breakdown

After a complete generation, the manifest groups payloads into
these categories that map to PDFE attack surface:

| Category | What it probes | PDFE mitigation |
|---|---|---|
| `js` | OpenAction, /AA, this.submitForm, getURL, etc. | MuJS sandbox; events not auto-fired |
| `launch` | /Launch action with external URL or shell | followLinkAt prompts via QMessageBox |
| `submitform` | /SubmitForm to URL or this.submitForm | FormSubmitter HostAllowlist |
| `uri` / `uri_unc` | /URI or UNC-form URI | Only followed via canvas click; phase-3 firewall blocks non-loopback |
| `goto` | /GoToE / /GoToR / /Thread | PDFE doesn't follow remote /GoTo |
| `xfa` | XFA forms with FormCalc / SOAP submit | No XFA renderer in PDFE |
| `xxe` | XXE in /XMP or /XFA streams | MuPDF disables external entity resolution |
| `embedded` | /AF Associated Files, RichMedia | Extraction is explicit user action only |
| `font` | Type1 FontMatrix, /FunctionType | PDFE uses MuPDF + FreeType, not affected |
| `eicar` | EICAR antivirus test pattern | Not a feature; AV will eat it before PDFE sees it |
| `svg_polyglot` | Non-PDF inputs | PDFE refuses non-PDF |
